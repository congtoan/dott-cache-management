## 0. Trong một đoạn

Trước đây mỗi URL có **2 bản HTML** (desktop và mobile), nên phải render 2 lần và lưu 4 file (`.html`, `_gzip` × 2). Hai bản chỉ khác nhau vài thẻ `<script>`. Đợt này đã đưa phần khác nhau đó vào **trình duyệt** (tt-core), cho plugin sticky sidebar dùng chung cơ chế, ép WP Rocket chỉ ghi **một bản**, và cho nginx trả thẳng file cache. Sau đó dựng 2 công cụ cho hệ thống mới: **Go uploader** trên VPS phụ (đẩy một bản HTML lên nhiều bucket S3 cùng lúc) và **prefork** trên VPS chính (render hàng loạt nhanh hơn khoảng 13 lần trên php81).

| | Trước | Sau (đã chạy trên php81) |
|---|---|---|
| Số lần render mỗi URL | 2 (desktop + mobile) | **1** |
| File cache mỗi URL | 4 + `.mobile-active` | **2** (`index-https.html` + `_gzip`) |
| JS theme trong HTML | `thongthai-script.js` hoặc `-mobile.js` tùy thiết bị | **một** `tt-core/core.js?ver=hash` cho mọi thiết bị |
| Sticky sidebar | thẻ `lss-N.js` chỉ in ở bản desktop | module trong `core.js`, tự quyết trong trình duyệt |
| Ai trả file cache | PHP (`advanced-cache.php`) | **nginx** (rocket-nginx), 5–13 ms |
| Upload S3 | Python tuần tự, 1 bucket | Go, pool nhiều luồng, **nhiều bucket**: 42,9 URL/s |
| Render 1.024 URL | 942 s qua HTTP | **73 s** bằng prefork |

## 1. Theme: tt-core, một file JS cho mọi thiết bị

**Vấn đề.** Mỗi child theme có 2 file JS riêng cho desktop và mobile, chọn ở PHP bằng `wp_is_mobile()`, nên HTML khác nhau theo thiết bị.

| Theme | Desktop | Mobile |
|---|---|---|
| `generatepress_child` (vi) | `thongthai-script.js` 70,8 KB | `thongthai-script-mobile.js` 49,8 KB |
| `generatepress_en` (en) | `thongthai-desktop.js` 28,0 KB | `thongthai-mobile.js` 20,2 KB |

**Cách làm.**
- Tách JS cũ thành **module**: 18 module cho vi, 8 cho en, trong `theme/generatepress_*/tt-core/modules/`. File nguồn viết rõ ràng, nhiều comment.
- Mỗi module khai báo thiết bị nó chạy: `TT.define(id, {ver, device: 'all'|'desktop'|'mobile', ready}, fn)`.
- `window.TT` (API 1) nhận biết thiết bị **giống `wp_is_mobile()`**: dùng `userAgentData.mobile`, nếu không có thì regex UA. Có thể ép bằng `?tt_device=mobile|desktop|auto` để test. Ngoài ra có `TT.ready`, `TT.load`, `TT.has`, `TT.list` và hàng đợi `TTQ`.
- **Build bằng PHP, không cần node trên server:**
  - kiểm cú pháp bằng Peast, minify bằng matthiasmullie/minify, rồi kiểm lại bản minify;
  - ghi file tạm rồi rename, giữ `core.prev.js` để quay về, có khóa `flock`.
  - Kết quả là một file cố định `themes/<child>/tt-core/core.js?ver=<hash>`, cache 1 năm (`immutable`) ở Cloudflare.
- **Build thủ công hoặc theo sự kiện, frontend không quét file.** Có 3 cách build: nút Generate trên dashboard, `wp tt-core build`, hoặc tự build ở lần mở admin kế tiếp sau khi có sự kiện đánh dấu (`tt_core_request_build`). Nếu có file vừa sửa trong 10 giây thì build tạm dừng (PENDING).
- **Hook cho plugin:** action `tt_core_modules( $reg, $theme )`, `tt_core_has_module()`, và thư mục `uploads/tt-core/<theme>/modules/` cho module plugin tự sinh.
- **Dashboard** ở Giao diện → TT Core: bật/tắt module, đổi thiết bị, kiểm tra cú pháp, Lưu và Generate, Quay về bản trước. WP-CLI có `wp tt-core status|check|build|rollback`.
- **Đường lui:** `functions.php` mới chỉ nạp engine khi file tồn tại (`is_file`). Nếu engine hỏng thì quay về nạp JS cũ. File JS cũ vẫn giữ, liệt kê trong `LEGACY-FILES.md`.

**Kết quả trên php81** (site 3 `/tttest/`, site 4 `/tttest-en/`):
- **vi:** 18 module, 90.355 byte gốc, minify còn **50.910 byte** (gzip 14,7 KB).
- **en:** 8 module, 37.085 byte gốc, minify còn **19.562 byte** (gzip 6,9 KB).
- Mỗi lần build mất khoảng 0,4 s.
- `verify-parity.js` cho thấy module ghép lại **khớp JS cũ** theo từng thiết bị. Chỉ lệch 2 chỗ có chủ đích (`xemthem`, `topOffset`).
- Desktop, mobile và iPad đều chạy đúng.
- Lỗi cú pháp thì build dừng và `core.js` cũ giữ nguyên.
- Rollback, đường lui và dashboard trên trình duyệt đều đạt.

**Để sau:** preload LCP trang chủ, wpDataTables (render bằng JS).

## 3. Một bản cache, bỏ bản mobile (WP Rocket 3.16)

**Đã tìm hiểu:**
- WP Rocket 3.16 **không có nút** tắt "Separate cache for mobile". Khi lưu thiết lập, nó tự bật lại `do_caching_mobile_files` nếu `cache_mobile` = 1.
- **Không được đặt `cache_mobile` = 0.** Lúc đầu mình đã làm sai như vậy trên php81. Khi đó `can_process_mobile` = false, nghĩa là **khách mobile không được phục vụ cache**.
- `advanced-cache.php` dùng chung cho cả mạng multisite. Nếu tạo nó từ một site đã tắt mobile thì file thiếu Mobile_Detect và hỏng các site khác. Đã tạo lại.
- File `_gzip` luôn được tạo (khi PHP có `gzencode`). Giữ file này, vì rocket-nginx trả thẳng nó.

**Cách giải:** mu-plugin [`wp/mu-plugins/dott-single-cache.php`](../wp/mu-plugins/dott-single-cache.php) ép `cache_mobile` = 1 và `do_caching_mobile_files` = 0, qua cả `option_` và `pre_update_option_` với độ ưu tiên `PHP_INT_MAX`:
- khách mobile vẫn được phục vụ cache;
- WP Rocket chỉ ghi **một bản**, dùng chung cho mọi thiết bị;
- không còn file `.mobile-active`.

**Kết quả trên php81:** mỗi URL chỉ còn `index-https.html` + `index-https.html_gzip`. Khách desktop và mobile nhận cùng một file, và tt-core lo phần khác nhau.

**Chưa làm trên production.** Thứ tự an toàn khi chuyển (design 5b):
1. deploy theme tt-core;
2. cập nhật plugin sticky 3.2.0;
3. cài mu-plugin;
4. xóa cache cũ theo từng đợt.

## 4. nginx trả thẳng file cache (rocket-nginx)

- **Đính chính:** trước đây **không có rocket-nginx**. File cache do PHP (`advanced-cache.php`) trả bằng `readfile`.
- Response render mới cũng có `Last-Modified`, nên dấu hiệu đúng của file cache là dòng `cached@` cuối HTML.
- Đã cài [`deploy/nginx/rocket-page-cache.conf`](../deploy/nginx/rocket-page-cache.conf) vào `/etc/nginx/extra/` và include cho **diaocthongthai.com** và **php81** (backup `*.conf.bak-2026-11-27`). congtoan.net không dùng WP Rocket nên không áp dụng.
- Thư mục cache nào còn `.mobile-active` thì nginx bỏ qua. Vì vậy trên production cấu hình này **chưa có tác dụng**, cho tới khi chuyển sang một bản HTML.
- Trên php81 (đã là một bản): nginx trả file trong **5–13 ms**, không chạy PHP.

## 5. S3 uploader bằng Go trên VPS phụ

**Thiết kế** (design 5b):
- VPS phụ lấy HTML **qua HTTP** từ origin. Không dùng scp/ssh, và không cần quyền đọc đĩa VPS chính.
- Mỗi URL chỉ lấy HTML một lần, rồi đẩy **song song lên mọi đích S3**. Mỗi đích có pool kết nối riêng.
- Nhiều đích theo châu lục. Đã test Chicago `us-ord-1` và Frankfurt `eu-central-1`, bucket `congtoanphp`.

**Code** (Go 1.26, **chỉ dùng thư viện chuẩn**):

| File | Việc |
|---|---|
| [`internal/s3/s3.go`](../internal/s3/s3.go) | Tự ký SigV4 path-style, Put/Head/Delete. Có `Content-MD5` và kiểm `ETag`. Không gửi `Expect: 100-continue` |
| [`internal/origin/origin.go`](../internal/origin/origin.go) | Gọi origin bằng IP, kiểm chứng chỉ bằng **SPKI pin**. Lấy lại tối đa 3 lần cho tới khi có `cached@`. Kiểm HTML lớn hơn 2 KB và có `</html>` |
| [`cmd/dott-cache/main.go`](../cmd/dott-cache/main.go) | Lệnh `upload` / `delete`, các cờ `-config -paths -limit -mobile-copy -log`. Key S3 = `prefix + path + index-https.html`. Header: `text/html`, `public, max-age=31536000`, `public-read` |

**Trên VPS phụ:**
- Binary ở `/opt/dott-cache/bin/dott-cache`.
- Cấu hình test ở `/etc/dott-cache/upload-test.json`.
- **Key S3 ở `/etc/dott-cache/s3.env`** (quyền 600). Claude trên VPS phụ bị cấm đọc file này, và key không bao giờ được in ra.
- Build bằng `GOMEMLIMIT=200MiB GOFLAGS=-p=1 go build`.

**Số đo** (1.024 URL × 2 bucket, php81):

| Trường hợp | Tốc độ | Lỗi |
|---|---|---|
| Đã có cache, 16 luồng mỗi đích | **42,9 URL/s** (≈ 86 PUT/s) | 0, md5 trên S3 khớp file trên đĩa |
| Phải render qua HTTP (cache trống) | 1,1 URL/s | 0 |

Vậy upload không còn là điểm nghẽn. Điểm nghẽn là **render**, và đó là lý do làm prefork.

**Khi đổi version CSS/JS** (design 5c): tool `rewrite-assets` sửa `?ver=` trực tiếp trong HTML cache (trên đĩa và S3), kết hợp purge Cloudflare, nên khỏi phải render lại toàn bộ. Cách này cũng giúp khách cũ đang có HTML trong cache trình duyệt. **Mới có thiết kế, chưa có code.**

## 6. Prefork: render hàng loạt và ghi cache WP Rocket thật

**Ý tưởng:**
- Tiến trình master nạp WordPress **một lần** (khoảng 0,4 s, phần lớn là 50 plugin).
- Sau đó `fork` cho từng URL. Mỗi tiến trình con chỉ chạy phần riêng của trang (khoảng 64 ms), rồi để chính WP Rocket ghi file cache.

**Script:** [`tools/prefork/prefork-render.php`](../tools/prefork/prefork-render.php), với các tham số `--root --host --urls --parallel --readonly --out --limit`, bật debug bằng `PF_DEBUG`. Đi kèm `compare-20.sh` (so với bản render qua HTTP) và `full-run.sh` (xóa cache, đo thời gian và load).

**Kết quả trên php81** (1.024 URL `/tttest/`):

| Cách render | Thời gian | URL/s | Load VPS chính |
|---|---|---|---|
| Qua HTTP (PHP-FPM) | 942 s | 1,1 | khoảng 1,1–1,2 |
| **Prefork, 1 tiến trình con** | **73 s** | **14** | trung bình 0,92 |
| Prefork, 2 tiến trình con | 74 s | 13,9 | trung bình 1,49 |

- Đủ 1.024 file `.html` và `_gzip`, **không có file mobile**, 0 lỗi.
- So 20 trang với bản render qua HTTP: **19/20 giống hệt** (sau khi bỏ các giá trị ngẫu nhiên: honeypot, nonce). Trang còn lại là trang chuyên mục. Danh sách bài của trang này cũng đổi giữa 2 lần render HTTP, nên không phải lỗi của prefork.
- Chạy 2 tiến trình con không nhanh hơn, vì VPS chính chỉ có **1 vCPU**. Dùng 1 tiến trình con.

**Các bẫy đã gặp và đã sửa:**
1. WordPress 6.9 chèn CSS block vào placeholder trong callback của bộ đệm output. Phải đóng bằng `ob_end_flush()`, không dùng `ob_get_clean()`.
2. `rocket_buffer` không tự chạy trong tiến trình con (`can_init_process` = false), nên script tự gọi `rocket_before_maybe_process_buffer` → `rocket_buffer` → `rocket_after_process_buffer`.
3. `WP_Rocket\Buffer\{Tests,Config,Cache}` ghi nhớ kết quả vào biến static, nên mỗi tiến trình con phải xóa phần ghi nhớ đó.
4. Notice PHP lọt vào HTML. Đã đặt `WP_DEBUG_DISPLAY` = false trên php81, giống production (có backup).
5. DB chạy ở chế độ READ ONLY khi chỉ đo. Tiến trình con tự kết thúc bằng SIGKILL để không chạy shutdown hook.

**Rủi ro và việc chưa kiểm chứng:**
- php81 **không có Redis**, nên render chậm hơn production. Trên production dự kiến prefork chỉ nhanh hơn **khoảng 3–5 lần**: 60.000 URL mất khoảng 1–1,5 giờ, so với 4–6 giờ qua HTTP. **Chưa đo trên production.**
- Script dựa vào API nội bộ của WP Rocket 3.16. Mỗi lần nâng cấp WP Rocket phải chạy lại `compare-20.sh`.

## 7. Những điều đã đính chính (đừng lặp lại)

- "nginx trả thẳng `_gzip` / sendfile" → **sai**. Trước 27/11 không có rocket-nginx, file do PHP trả.
- "Có `Last-Modified` nghĩa là file cache" → **sai**. Dấu hiệu đúng là `cached@`.
- "Đặt `cache_mobile` = 0 để có một bản" → **sai**, khách mobile mất cache. Dùng mu-plugin `dott-single-cache`.
- "Prefork 2 tiến trình con sẽ nhanh gấp đôi" → **sai** trên máy 1 vCPU.
